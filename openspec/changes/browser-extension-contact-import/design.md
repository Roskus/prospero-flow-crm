# Design

## Context

- The API authenticates with JWT (`auth:api`, php-open-source-saver/jwt-auth): `POST /api/auth/login` returns `access_token` and `expires_in`; `POST /api/auth/refresh` works with an expired token inside `refresh_ttl` (14 days); `POST /api/auth/me` returns the user; `POST /api/auth/logout` blacklists the token. Inactive users get `403 Inactive user`.
- The token lifetime is configurable (`jwt.ttl`, `JWT_TTL`, in minutes, default 60). jwt-auth treats a `null` TTL as tokens that never expire, and an empty `JWT_TTL` would become 0. `respondWithToken()` reports `expires_in` as `TTL * 120`, twice the real lifetime in seconds, so a client that trusts it refreshes too late.
- CORS allows any origin on `api/*` and the API does not use cookies, so a bearer token is enough.
- `POST /api/contact` accepts `lead_id` or `customer_id` (validated against the company, soft-deleted rejected), optional email and phone, `contact_linkedin`, `contact_job_title` and the address fields.
- `POST /api/lead` requires `name`, `seller_id` (of the company) and `country_id`.
- `GET /api/lead`, `/customer` return `{count, <plural>, ...pagination}`; `GET /api/contact` returns `{count, contacts}` without pagination. Lead visibility is company-wide for every seller (no seller scope).
- The repository has no `package.json` and must not gain dependencies. Node is not available on the server and the extension must not need it.

## Goals / Non-Goals

**Goals:**
- One extension source for Chrome, Edge and Firefox, loadable unpacked, with no build step.
- The API token never reaches the LinkedIn page's JavaScript.
- Vanilla JavaScript as simple as possible: no Node, no npm, no bundler, no modules, no frameworks.
- LinkedIn parsing isolated in plain functions that can be tested by opening a page in the browser.

**Non-Goals:**
- Publishing to the Chrome Web Store, Edge Add-ons or AMO (packaging and listings come later).
- Capturing, storing or showing contact photos, in any form.
- Capturing email or phone from LinkedIn, Sales Navigator or company pages.
- Updating an existing contact from the extension (it only warns and links to it).
- Offline queueing or syncing.

## Decisions

### Extension structure
```
browser-extension/
  manifest.json        MV3, default_locale en, gecko id
  _locales/{en,es}/messages.json
  background.js        CRM client and token: login, refresh, logout, search, create lead/contact
  linkedin.js          plain functions: read the profile, split the location, normalize the profile URL
  content.js           LinkedIn page: detects profiles, "Add to CRM" button, opens the panel
  panel.html/.js/.css  contact form shown in an iframe on the profile
  popup.html/.js/.css  login form, current user, logout
  icons/
  tests/tests.html     opens in the browser and runs the linkedin.js checks with fixtures
```
Classic scripts, no ES modules, no build: `linkedin.js` defines plain global functions and is listed before `content.js` in the content script; `tests/tests.html` loads it with a `<script>` tag. **Alternative**: ES modules or TypeScript with a bundler — rejected, they add a build step or Node, and content scripts cannot be modules anyway.

### Cross-browser manifest
One `manifest.json` with `background.service_worker` (Chrome, Edge) and `background.scripts` (Firefox) pointing to the same `background.js`, and `browser_specific_settings.gecko.id` (required by Firefox for storage). The code uses the `chrome.*` namespace with promises, which Chrome, Edge and Firefox support in MV3, so no compatibility shim is needed. **Alternative**: one manifest per browser generated by a script — rejected while a single manifest loads in all three; verified manually in each browser as a task.

### Token lives in the background only
`background.js` keeps the session; the popup and the panel talk to it through `runtime.sendMessage`. The content script only reads the page and opens the panel; it never sees the token or calls the CRM. The token and CRM URL are kept in `storage.local` (never `storage.sync`, which would copy the token to other devices). The password is sent once to `login` and discarded.

### CRM origin as optional host permission
`optional_host_permissions: ["https://*/*", "http://*/*"]`; at login the popup calls `permissions.request({origins: ["<crm origin>/*"]})` from the user's click (both browsers require a user gesture). Requests from the background with that permission are not blocked by CORS. **Alternative**: fixed `host_permissions` for `crm.roskus.com` — rejected, every installation has its own CRM URL. `http://` is allowed only for local development; the popup warns when the URL is not `https`.

### Token refresh
`background.js` stores `expires_at = now + expires_in` and refreshes when a request is due within 5 minutes of it, or on a `401` retried once after `refresh`. A failed refresh or `403 Inactive user` clears the session. `jwt.ttl` falls back to the 60 minutes default when `JWT_TTL` is missing or empty, like other Laravel settings, so API tokens always expire; never-expiring tokens are not supported because a stolen token would work forever. `respondWithToken()` reports `expires_in` = TTL × 60 seconds; login and refresh share it, so both report the same value.

### Panel in an iframe
The form is the extension page `panel.html`, inserted by the content script as a fixed side iframe (`web_accessible_resources` restricted to `https://www.linkedin.com/*`). The content script sends the parsed profile to the panel with `postMessage` to the iframe's extension origin. **Alternative**: inject the form into the page with a shadow root — rejected, the panel would run in the content script context next to LinkedIn's page and share its DOM events; the iframe keeps the form, its CSS and the messaging with the background isolated.

### LinkedIn is a single page app
The content script matches `https://www.linkedin.com/*` and watches URL changes (`navigation` events where available, otherwise a `MutationObserver` on `document.title`), showing the "Add to CRM" button only on `/in/<slug>` paths. It reads the profile only when the button is clicked, never in the background.

### Profile parsing
`linkedin.js` takes the profile `main` element and reads: the `h1` (full name, split on the first space into first and last name), the headline (`Job title at Company` / `Job title | Company`), the location line and the current company from the top card button or the first experience entry. It never reads images. Each read is wrapped so a missing element yields an empty field. Selectors are kept in one table at the top of the file so a LinkedIn markup change is a one-place fix. Checked with saved HTML fixtures (anonymised, no real people, images removed) in `tests/tests.html`, a page that runs each case and lists passed and failed checks; it is opened from the loaded extension, no tooling needed.

### Location
The location function in `linkedin.js` splits LinkedIn's `City, Province, Country` (also `City, Country` and `Country` only) and maps the country name to its ISO code with a small embedded table (English and Spanish names of the countries the CRM uses, unknown names left for the user to pick in the form's country select, filled from the same table).

### Search on lists (backend)
`search` is an optional, max 120 characters query on `GET /api/lead` and `GET /api/customer`, applied as `name LIKE %search% OR business_name LIKE %search%` with `%` and `_` escaped, before pagination; pagination links already keep the query (`paginatedListResponse`). It does not reuse `Lead::getAllByCompanyId()` because that method mixes web filters and full-text search; a small scope `search()` on `Prospect` keeps it shared by leads and customers. Validation in Form Requests (`LeadListRequest`, `CustomerListRequest`).

### Contact lookup by LinkedIn URL (backend)
`linkedin` on `GET /api/contact` is normalized to the profile slug (`/in/<slug>`, lower case, without scheme, `www.`, query or trailing slash) and matched against contacts whose `linkedin` contains `/in/<slug>` followed by end, `/` or `?` (three escaped `LIKE` patterns OR-ed). The response keeps `{count, contacts}`; `contacts` carries `lead_id` and `customer_id` so the extension can link to the owner. The same normalization is implemented in `linkedin.js` for the extension; the PHP tests and `tests/tests.html` use the same cases.

### New lead
The panel calls `POST /api/lead` with `name` = company, `seller_id` = the user from `me`, `country_id` = the form country or the user company's country (read once at login with `GET /api/company/{company_id}`), `linkedin` = the company page URL when the profile shows it. Then it creates the contact with the returned id.

## Risks / Trade-offs

- [LinkedIn changes its markup and the parser stops filling fields] → missing fields stay empty, the form is fully editable, selectors live in one table and fixtures make the fix quick.
- [LinkedIn terms forbid scraping] → the extension reads only the open profile after a click; no crawling, no background reads, no bulk import.
- [Same manifest not accepted by a future browser version] → manual check in the three browsers is a task; splitting the manifest per browser is a contained fallback.
- [Token stolen from a compromised browser profile] → token lifetime is the API's TTL (60 minutes), refresh limited to 14 days, logout blacklists it; the password is never stored.
- [`LIKE %search%` is slow on large tables] → search is limited to one company and paginated; full-text search can replace it later without changing the API.
- [Fixing `expires_in` changes the login response] → no API consumers exist yet; the value becomes correct, the shape stays the same.

## Migration Plan

- Backend changes ship as a normal deploy; no migrations.
- The extension is loaded unpacked from `browser-extension/` (Chrome/Edge: Developer mode → Load unpacked; Firefox: `about:debugging` → Load Temporary Add-on). Rollback: remove the extension; the API additions are optional query parameters.

## Open Questions

- Store publication (accounts, listing texts, icons per store) — separate change once the extension is used internally.
