# Design

## Context

- Address columns today:

  | Table | country_id | province | city | locality | street | address_extra | zipcode | latitude / longitude |
  |---|---|---|---|---|---|---|---|---|
  | `lead`, `customer` | 2 | 80 | 50 | 80 | 80 | 80 | 10 | decimal(11,8) |
  | `company` | 2 | 50 | 50 | - | 80 | - | 10 | - |
  | `supplier` | 2 | 50 | 50 | - | 80 | - | 10 | - |

- `Lead` and `Customer` extend the abstract `Prospect` model. Each entity has a repository that copies request fields to columns one by one; `LeadRepository` and `CustomerRepository` skip `address_extra`.
- Validation lengths differ per request (`CompanySaveRequest` allows 255 for province, city and street; the supplier API allows 255).
- The search and map are anonymous Blade components (`components/geolocalization/search` and `map`) using fixed element ids (`search-address`, `latitude`, `longitude`), so there is one map per page. Search uses Nominatim and only fills the coordinates.
- Country is stored as the lowercase ISO code (`code_2`) and selected with `components/country`.

## Goals / Non-Goals

**Goals:**
- One definition of the address (fields, lengths, rules, formatting, form, display) reused by every entity, with no change to how data is stored or queried.
- Lead/customer list filters, CSV import/export and existing API fields keep working without changes.

**Non-Goals:**
- Several addresses per entity (billing / shipping). Planned path for a later change: keep the main address in columns (filters, search, imports) and add nullable JSON columns such as `billing_address` and `shipping_address` (null = same as the main address), cast to the same `Address` object. They are only read when invoicing or delivering, never filtered, so JSON fits them. `Address` keeps `fromArray()`/`toArray()` symmetric so the JSON cast is trivial.
- Filling street, city, etc. from the search result (reverse geocoding). Search keeps filling only the coordinates.
- Bank addresses (`bank.country_id`), which only store a country.

## Decisions

### Columns per entity + `Address` value object, no address table
A polymorphic `address` table would define the fields once but needs moving data out of four tables, joins or eager loading in every list, and rewriting the province/country filters, imports and API. Keeping the columns in each table and mapping them to an immutable `App\ValueObjects\Address` gives the same reuse in code with no data migration. The repetition of physical columns is generated by one schema macro.

### `Address` value object
Readonly properties `countryId`, `province`, `city`, `locality`, `street`, `extra`, `zipcode`, `latitude`, `longitude`. Methods:
- `fromArray(array $data): self` from request/import keys (`country_id`, `address_extra`...), trimming and turning empty strings into null, lowercasing the country.
- `toArray(): array` back to column names.
- `isEmpty()`, `hasCoordinates()`.
- `lines(): array` (`street, extra`, `locality`, `zipcode city`, `province`, country name) skipping empty parts, and `oneLine(): string` joining them with ", ". The country name comes from the `Country` model, cached.

`Address` implements `Castable`, so it is its own Eloquent cast: `get()` builds it from the model attributes and `set()` returns the column array. Multi-column casts are supported by Eloquent.

### `HasAddress` trait
`App\Traits\HasAddress` adds the `address` cast through `initializeHasAddress()` (merging into `$this->casts`) so models only add `use HasAddress;`. Used in `Prospect` (lead and customer), `Company` and `Supplier`, and later `Branch`. Repositories replace the per-field copy with `$model->address = Address::fromArray($data)`.

### Schema macros
`Blueprint::macro('address', ...)` in `AppServiceProvider` creates all nullable address columns with the lengths of the lead/customer table (the most complete). New tables (`branch`) use `$table->address()`. A migration adds the missing columns to `company` and `supplier` and widens `province` to 80; it lists the columns explicitly instead of using the macro, so the migration stays reproducible if the macro changes later.

### Contacts: rename `country` to `country_id`
`contact` and `supplier_contact` store an unused `country` column (no form, repository or API writes it). Renaming it to `country_id` keeps one column naming for `Address` instead of teaching the cast per-model column names. The only visible effect is the key in contact API responses (`country` → `country_id`), marked as breaking in the proposal. The contact forms post the address with the standard field names (`country_id`, `city`...) next to their `contact_*` fields, and the save controllers get a `ContactSaveRequest` with `AddressRules` (they validate nothing today).

### `AddressRules`
`App\Rules\AddressRules::rules(bool $countryRequired = false): array` returns the rules keyed by request field, using the existing `CountryRule` for the country. Requests merge it (`[...AddressRules::rules(true), ...]`). Lengths: province 80, city 50, locality 80, street 80, address_extra 80, zipcode 10, coordinates as in `LeadRequest` today.

### Blade components
- `components/address/form.blade.php`: receives an `Address` (or the model) and optional `required` for the country and `class` for the input size; renders search, `components.country`, the text fields, hidden coordinates and the map. Values use `old()` with the address as fallback.
- `components/address/display.blade.php`: receives an `Address` and a `format` (`lines` or `inline`); prints nothing for an empty address. Plain HTML so it also works inside the dompdf PDF.

## Risks / Trade-offs

- [Multi-column cast and dirty tracking: assigning `address` sets several columns] → covered by tests that update one field and keep the rest; audit (`created_by`/`updated_by`) is unaffected.
- [Map component relies on fixed ids, so only one address form per page] → accepted; no screen needs two. Documented in the component.
- [Widening `province` on `company`/`supplier`] → only enlarges; no data loss. The `down()` shrinks it back only when no value is longer than 50, otherwise it leaves it.
- [Leaflet and Nominatim load on company and supplier forms too] → same assets already used by lead/customer; loaded only on form pages.

## Migration Plan

1. Migration adding `locality`, `address_extra`, `latitude`, `longitude` to `company` and `supplier` and changing `province` to `varchar(80)` (keeping nullability).
2. Deploy code; no data backfill needed.

Rollback: drop the added columns; existing columns are untouched.
